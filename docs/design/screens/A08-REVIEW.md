# A08 Staff Access

**Mode · Operate. Status · Research and layout alternatives.** The user approved Layout A and A08-C05 on 25 November 2026. [Approved Pen.dev handoff](A08-SHAPE.md)

A signed-in RAFIQ Owner opens **Staff Access** in the internal admin navigation to check who has access, invite Staff, change individual grants, appoint an eligible Owner, or reset another administrator’s authenticator enrollment. The Owner can identify the exact target and see what will change before committing. A confirmed change produces a readable outcome and an audit record. A01 handles invitation redemption and entry, A02 supplies fresh verification and enrollment, A03 handles MFA recovery, and A09 provides audit review. A07’s driver account suspension is a distinct action governed by the effective Staff permissions below. ## Layout concepts

| Concept | Desktop composition and operation | Trade-off |
| --- | --- | --- |
| **A · Roster with an inline access editor** · recommended | Use the internal admin shell. Align **Staff Access** with **Invite staff** above an **Administrators** table. Open **Manage access** directly under its row, one administrator at a time. Put current grants above editable draft grants, then show **Review changes** and separate **Owner role**, **Revoke admin access** and **Reset authenticator** actions as eligible. Invitations and sensitive confirmations use the existing centered dialog treatment. | Keeps the target close to its permissions through review and narrow reflow. A long editor pushes the next rows down. This extends A05’s table and companion-row arrangement. |
| **B · Roster and selected administrator** | Use the same heading and invitation action. Show a compact roster on the left and a persistent detail panel on the right with the selected identity, access state, permissions and eligible actions. At narrow widths place the same labeled detail beneath the selected item and restore focus to that item on close. | Keeps the roster shorter when switching between people. The right panel competes with the roster for width and needs a persistent selection cue and an explicit close/back path. |

**Layout A** makes it easier to confirm that the editor belongs to the same administrator you selected, especially under zoom. Use the same stable row order during edits and refreshes. Desktop columns are **Administrator**, **Role**, **Access**, **Assigned permissions**, and **Manage**. At narrow widths use a labeled list with the same field order, then open the editor beneath its item. Use **Load more** when the server supplies a cursor. Use the roster table to present and compare access data. Design fixtures should cover one Owner with no Staff, two active Owners, active Staff with multiple scopes, enrollment required, a revoked principal when present in the response, a long ID, and a second page. These fixtures establish no expected roster size. [Related table layout](A05-SHAPE.md) · [Roster contract](../../API.md#7-detailed-endpoint--operation-specifications)

## Content and components

- **Roster.** Use the authorized **Admin ID** as the visible identifier supported by the current API. Retain the full ID as wrapping text in the editor and confirmation. Show **Owner** and **Staff** as role labels and **Active**, **Enrollment required**, or **Access revoked** from the returned state. Present Staff grant names in a consistent order. On Owner rows, show **Included with Owner role** for effective access and label separately any explicit grants the server returns. Appointment and removal eligibility require server evidence. [StaffPrincipal and StaffPage](../../API.md#7-detailed-endpoint--operation-specifications)
- **Permission editor.** Use labeled checkboxes for **View metrics**, **Account support**, and **Suspension**. Explain what each authorizes. Put “Suspend and reinstate require Account support as well as Suspension” beside the Suspension checkbox. Preserve independent assignments. If Account support is removed while Suspension stays assigned, the review explicitly shows that suspend and reinstate will become unavailable. If Suspension is selected alone, show **Assigned · Account support required to use** wherever effective access is explained. A change updates the local draft immediately and the saved roster only after confirmation by the server. [Permission definitions](../../TRD.md#71-admin-dashboard-fr-22)
- **Invitation dialog.** Use **Invite staff**, a labeled **Registered email** field, the same three Staff permission checkboxes, then **Review invitation**. Review the exact email and grants under **Create staff invitation?** Explain single use, expiry, the verified email match and authenticator enrollment before admission. Reuse the dialog for verification and then **Create invitation**. On confirmed creation, show **Invitation created**, the selectable link, **Copy invitation link**, and an absolute expiry date, time and zone taken from `expiresAt`. Give inline copy success and a manual selection fallback. Use **Invitation expired** if it expires while shown. Closing the result, leaving the workspace, expiry or loss of authority clears the local link. Use the approved admin origin for the returned path. A01 owns validation, redemption and recipient states. [A01 handoff](A01-SHAPE.md) · [Invitation API](../../API.md#7-detailed-endpoint--operation-specifications)
- **Existing RAFIQ components.** Use the A05 horizontal and stacked status rows (`Yh4JZ`, `fqIDy`) and internal shell convention, the D20 checkbox (`B720aK`) and D24 permission row (`JoMRk`) as control references, the centered confirmation frame (`f1ZMyr`), and A02’s verification and confirmation-restored storyboard (`ITZ0z`) and OTP field family. Reuse the established buttons, text fields, focus treatments and status language. The A02 storyboard, D24 permission row and confirmation frame were inspected visually on the RAFIQ canvas. [RAFIQ canvas](<../../../Pen Design/RAFIQ.pen>) · [A02 handoff](A02-SHAPE.md)
- **Standard components.** Use a semantic table or narrow labeled list, native labeled fields and checkboxes, headings, buttons, a modal dialog, and inline status and error text. **New RAFIQ compositions** are the roster/editor, permission change summary, current-versus-draft conflict view, and invitation receipt. External options affect only the bounded presentation in the research table. [Table semantics](https://www.w3.org/WAI/tutorials/tables/) · [Modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

Use `colors.canvas`, `colors.ink` and `colors.accent-stone`, the existing RAFIQ verification focus treatment and Space Grotesk as the documented Mori substitute. Follow the existing admin gutters and flat dividers. Use `spacing.xl`, `spacing.md` and `spacing.sm` (24, 16 and 8 px) for sections, groups and related labels. Keep access state in words and reserve accent color for existing action, focus and status roles. [Visual tokens](../../DESIGN.md)

## Review, verify and commit

Keep one dialog and one named target through review, **Verify to continue**, and the returned confirmation. Show the target, operation, exact change and consequence above the A02 authenticator field. A successful challenge returns **Identity verified** and restores the named final action. The Owner explicitly activates that action. If freshness expires, show **Verify again to continue** and preserve the draft while it remains authorized and applicable. Invalid, reused and rate-limited codes use A02 feedback. Before accepting a write, the service rechecks the acting Owner’s current authority, fresh verification and target eligibility. [A02 confirmation behavior](A02-SHAPE.md#returning-sign-in-and-sensitive-actions) · [Session and access checks](../../TRD.md#71-admin-dashboard-fr-22)

| Operation | Review and confirmed outcome |
| --- | --- |
| **Save permissions** | Display **Added** and **Removed** grants with their names and effective consequences. If a grant is removed, say it takes effect immediately. On success update the matching row and announce **Permissions updated**. Name the removed permission in the result when applicable. |
| **Revoke admin access** | Show the target’s current role and “They will lose access to the internal dashboard immediately, including in open sessions.” Confirm with **Revoke admin access**. On server success apply **Access revoked** and clear any affected views, controls and cached protected data in the affected session as soon as invalidation is known. Apply the same clearing to pending responses and dialogs. |
| **Appoint Owner** | Offer only to Staff whose current eligibility and MFA protection are established. Explain that the Owner role includes all dashboard permissions plus managing Staff Access and viewing Audit. Use **Appoint Owner** as the final action. An eligible demotion uses **Change to Staff** and shows the exact resulting Staff grants and loss of Owner privileges. Recheck the last-Owner rule for any change that removes an active Owner. |
| **Reset authenticator** | Offer for another administrator only when the service confirms eligibility. Explain that their existing admin session authority ends and they must sign in and enroll again. Confirm with **Reset authenticator**. After a confirmed reset, show an inline outcome and reload the target’s access state. A03/A02 handle eligible recovery and new enrollment. Loss of the last Owner’s authenticator and recovery codes follows audited deployment recovery. [A03 handoff](A03-SHAPE.md) |

## States the design must show

| State | Proposed presentation and recovery |
| --- | --- |
| Loading, no Staff, load failure | Keep the shell and heading. Use **Loading administrators…** for the initial read. An Owner-only roster keeps the Owner row and shows **No staff administrators yet** with **Invite staff**. A wholly empty authorized response shows **No administrators returned** and **Reload**. A read failure names the failed roster/page and offers **Retry**. Any visible earlier rows are labeled **Last loaded results** and changes require fresh data. |
| Saving or verifying | Use local status such as **Verifying…**, **Saving permissions…**, or **Creating invitation…** while the operation is pending. Prevent duplicate submits. Announce the server-confirmed outcome once in the originating workspace or invitation receipt. |
| **Permission conflict** | Example: another Owner changed this administrator while the draft was open. Show **Permissions changed while you were editing** with **Current permissions** and **Your draft**, and identify any change to the role or access state. **Reload and review** fetches current grants. Preserve the old selection as a reference only while authorized, then require the Owner to reapply the intended changes against the new starting state and run review again. Disable the stale confirmation. A business-rule rejection identifies the conflicting permission or state and returns to the affected field. The Account support prerequisite is shown ahead of confirmation as an effective-access rule. |
| **Last Owner protected** | When the service confirms the target is the last active Owner, explain next to protected actions “At least one active Owner is required.” If a concurrent change produces `last_owner_required` at commit, show **This is the last active Owner** with **Back to staff access**. Reload the roster, keep destructive actions unavailable for that target and explain that another eligible MFA-protected admin must be appointed first. |
| Save failure, rate limit, uncertain result | A known rejection shows an action-specific error and preserves eligible inputs. On rate limit, show when another attempt is allowed if provided. On lost response show **Couldn’t confirm the result** and reconcile with current server state before any retry. A lost invitation receipt provides no usable link. Reissuing an invitation or repeating an MFA reset requires a qualified operation-specific recovery path. |
| **Authority lost during review, verification or write** | On current ownership loss, sign-out or session invalidation, close the working dialog and clear the affected roster, draft, invitation link and late responses immediately. Resolve present admin entry. A demoted Owner can go to a still-permitted admin view. A revoked administrator sees the applicable A01 access state. If the Owner retains authority and only the target changed, show the eligible current target state or a safe **Administrator unavailable** outcome. |

## Accessibility and Pen.dev review frames

- Draw the chosen composition at **1440 px**, a **1024 px** compact desktop and a **320 CSS px** single-column reflow. Verify **200% browser zoom** in the frontend. Allow long identifiers and links to wrap. Keep modal content scrollable in one axis and focus visible. Give each row action an accessible name that identifies the target, group the checkboxes under **Permissions**, and use text for grants, conflicts and protection. [WCAG reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) · [Table semantics](https://www.w3.org/WAI/tutorials/tables/)
- In the modal, focus the heading or first field for form entry and the non-destructive option for the final destructive confirmation where appropriate. Trap Tab and Shift+Tab, support Escape for safe cancellation, and restore focus to the originating control or safe surviving heading. Keep step changes within the same modal. Associate errors and help with their fields and announce asynchronous results once. [Modal focus guidance](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)
- Storyboard the roster, edit draft, invitation entry and receipt, fresh verification and verified return, permission conflict, successful revocation, denied last-Owner change, eligible appointment and reset, loading, empty, failed save, uncertain outcome, and a cleared workspace after authority loss. Use fictional UUIDs, example domains, inert invitation links and synthetic dates. If selected, show the optional motion’s 0 ms and settled frames and a reduced-motion frame at the final state. Never wait for an animation to reveal an error, apply a result or clear access. The frontend must qualify keyboard focus, announcements, account transitions, revalidation, concurrency and motion preference behavior.

## Open contract details

- The proposed roster provides UUID, role, state, permissions and cursor. Confirm any friendlier authorized identifier, actor/target action eligibility and the scope of retained revoked rows before designing with those fields. The listed endpoints do not expose an invitation list, delivery state, resend or revocation action. The create receipt is the invitation-management surface supported today. [Admin endpoints and schemas](../../API.md#7-detailed-endpoint--operation-specifications)
- Define the write precondition and conflict response that let the frontend detect a stale edit before overwriting another Owner’s changes. `putStaffAccess` currently shows a full replacement body and a generic `409`. Confirm supported permission combinations, protected actions when reset would leave no active Owner, and the way an open view learns authority is gone. Server-side last-Owner serialization and per-request current grant checks are specified. [Access API](../../API.md#7-detailed-endpoint--operation-specifications) · [Administration architecture](../../ARCHITECTURE.md#module-m09--administration)
- Confirm invite-link recovery and duplicate handling after an ambiguous create, the verified admin origin and display time zone, and any response detail required to reconcile ambiguous resets. Use server `expiresAt` for all invitation deadline copy and a fresh server state for access copy. [Invitation and reset contracts](../../API.md#7-detailed-endpoint--operation-specifications)
