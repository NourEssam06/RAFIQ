# A07 Account Support

**Mode** · Operate. **Status** · Review completed on 25 November 2026. [Approved Pen.dev handoff](A07-SHAPE.md)

An authorized Owner or Staff member opens **Account Support** from the restricted admin shell, or lands there after A01 and A02 when it is their first permitted view. They locate one known driver account, verify that it is the intended target, and complete an eligible support action. Navigating away clears the lookup and action draft. A02 supplies fresh verification inside A07, A03 handles authenticator recovery, A09 owns the Owner-only audit view, and D22 owns driver account deletion. [Screen requirements](../../SCREENS.md#a07-account-support) · [J8 support journey](../../EXPERIENCE.md#j8-operate-rafiq-and-support-an-account)

Use a readable status label and reserve the strongest action emphasis inside the confirmation dialog for the named commitment. ## Exact lookup and five-field record

- **Lookup.** Use one visible label, **Registered email or account ID**, with “Enter the full registered email or account ID.” Submit with **Find account** or Enter. Allow paste, turn off spellcheck and capitalization, and use server-side identity-provider normalization and exact matching. A recognized invalid format gets a field error. Avoid live suggestions, browse lists, recent accounts, and identifiers in URLs. Editing or clearing the query immediately removes the previous record and actions. Ignore late results from a superseded lookup. [USWDS Search](https://designsystem.digital.gov/components/search/) · [Lookup contract](../../API.md#7-detailed-endpoint--operation-specifications)
- **Account record.** Use one heading and a semantic description list. Display exactly **Account ID**, **Registered email**, **Verification status**, **Account status**, and **Signup date**, in that order. Use literal **Verified / Unverified** and **Active / Restricted**. Keep email and UUID selectable and wrap long values without dropping characters. Use a localized, unambiguous signup date, with the date basis agreed against the API timestamp. Use synthetic values in Pen.dev. Keep other driver data and audit details outside the record. [GOV.UK Summary list](https://design-system.service.gov.uk/components/summary-list/) · [A07 field allowlist](../../SCREENS.md#a07-account-support)
- **Action area.** Place **Request verification email** for an eligible unverified account or **Request recovery email** when the identity lifecycle permits it. The registered address can appear as the fixed destination. The server binds it to the target account. Keep the request feedback adjacent to the action and independent of lookup progress. If the account has no eligible actions for the viewer, display “No support actions are available for this account.” Keep the record readable while the viewer remains authorized. [Support permissions and identity lifecycle](../../TRD.md#71-admin-dashboard-fr-22)

## Suspend or reinstate

Show **Suspend account** for eligible active accounts and **Reinstate account** for eligible restricted accounts when the viewer is an Owner or holds both Account support and Suspension. The result feature uses the A02 modal pattern and never presents both lifecycle actions for the same snapshot. [A07 requirements](../../SCREENS.md#a07-account-support) · [Modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

1. **Review.** Name the action and target using the registered email and account ID. For suspension, explain that hosted access and sync stop and existing hosted sessions and grants lose access. Add “A monitoring session already running offline keeps its local warnings within its existing limits.” For reinstatement, explain that the driver must sign in again and grant fresh consent before reconnecting an MCP client. Require **Reason** with an unselected “Select a reason” prompt and approved, action-specific labels. Use a native select as the default. A short, stable reason list can use a radio group if all labels fit comfortably. An unavailable catalog blocks progression. [Suspension boundary](../../TRD.md#71-admin-dashboard-fr-22) · [GOV.UK Select](https://design-system.service.gov.uk/components/select/) · [GOV.UK Radios](https://design-system.service.gov.uk/components/radios/)
2. **Verify.** **Continue to verification** opens the A02 challenge in the same dialog. Keep the action, target and reason visible. Reuse a single labeled, pasteable authenticator field with six visual slots, adjacent feedback and **Verify to continue**. Clear the code after submission or dismissal. The A03 recovery link leaves the privileged flow. After successful verification, return to the confirmation phase with **Identity verified** and a separate **Suspend account** or **Reinstate account** button. [Approved A02 handoff](A02-SHAPE.md)
3. **Commit.** Keep the target fixed while the dialog is open. Verify current grants, fresh verification, reason validity and target eligibility at the server before committing. Prevent duplicate submits. While submitting, show the specific in-progress status and preserve the draft for recoverable failures scoped to the same target and action. On confirmed success, replace the record from the returned five fields, close the dialog and announce **Account suspended** or **Account reinstated** in the action area. [Lifecycle API](../../API.md#7-detailed-endpoint--operation-specifications)

## State and recovery

| State | Visible behavior |
| --- | --- |
| Initial, searching, no match | Start with the form and exact-match hint. Show “Searching…” beside the form during a single outstanding lookup. For an authorized definitive miss show “No account matches that email or account ID.” Keep the value editable and omit the account record. |
| Lookup unavailable or rate limited | Show “Couldn’t look up the account. Try again.” or “Too many lookup attempts. Try again later.” Honor a server retry hint when supplied. Keep the query available to correct or retry. |
| Message offered, pending or accepted | Show the eligible message kind and fixed destination. After a 202 acknowledgement say “Verification email request accepted” or “Recovery email request accepted.” An acknowledgement means processing has been accepted. |
| Message limited, unavailable or unconfirmed | Keep the outcome near the action. For an ambiguous response say “We couldn’t confirm the email request.” Use the same idempotency key if the same intent is retried. Gate any retry on current eligibility and the server's retry hint. |
| Verification waiting, rejected, limited or expired | Show progress next to **Verify to continue**. For invalid or reused codes use “That code couldn’t be verified. Enter a new code from your authenticator app.” Honor rate limits. If fresh verification expires, bring the admin back to the challenge and retain the selected reason for that target and action. |
| Reason rejected, account changes, or update unconfirmed | A still-valid reason stays selected through recoverable errors. If rejected, focus Reason and ask for an approved selection. For a conflict, recheck the account and require a new review if the action changes. After an ambiguous commit say “We couldn’t confirm the account change.” Reconcile via an authorized refresh or identical retry as the contract permits. Claim action success only when confirmed. |
| Suspension permission removed | Close the privileged dialog and clear its code, draft and privileged controls. Retain authorized lookup and eligible messages while Account support continues. |
| Account support, admin session or target unavailable | On known loss of support authority, clear query, record, drafts and in-flight updates immediately, then route to the current permitted view or admin entry. On target withdrawal, clear its record and actions and return focus to the lookup. Ignore late responses after authorization or target changes. |

Use a quiet live status for search, verification and ordinary success. Associate field errors with their controls and use an alert for blocking errors that need immediate attention. Feedback can say what staff can do next while keeping provider errors, message payloads and credentials private. [WCAG Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) · [API response and retry rules](../../API.md)

## Pen.dev review and open dependencies

- Review a 1440 px matched viewport, a narrow desktop viewport and a 320 CSS px reflow with a long email and full UUID. At 200% browser zoom and 320 CSS px, stack the form, labels, values and dialog actions in reading order. Keep a single content scroll axis with focused controls visible. Use a visible skip link, label associations, keyboard access, legible contrast and text for every status. [WCAG Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- Use the modal heading as initial focus when the consequences need reading. Keep Tab inside the dialog, allow cancellation before submission and return focus to the initiating control where it still exists. After success or revocation, focus the surviving status or lookup/navigation target. Pen.dev frames should show a keyboard focus example, reason selection, verification, verified return, confirmed success and recovery states. Frontend qualification covers focus restoration, live announcements, reduced motion, stale responses, ambiguous retries and immediate permission withdrawal. [W3C dialog keyboard guidance](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/#keyboardinteraction)
- Confirm the approved reason codes and staff-facing labels, the exact identity-message eligibility rules and how the UI gets them within the five-field data boundary, the freshness window and retry/error mapping for A02, and the signup-date display basis. The API defines a reason string and one example, plus a 202 acceptance response for messages. Use annotated placeholder reasons in Pen.dev until there is an approved catalog.
