# D24 MCP authorization

**Approved design.** Use a single-column review with native checkboxes, a brief disclosure transition, and immediate selection and outcome feedback. D24 is an Operate screen for a signed-in, eligible driver reviewing a request initiated in a compatible external client. The driver should be able to recognize the requester, understand each permission, and grant either permission, both permissions, or neither. Setup and authorization take place while stationary. [D24 screen requirements](../../SCREENS.md#d24-mcp-authorization) · [Experience](../../EXPERIENCE.md)

## Layout and copy

Use a dedicated RAFIQ browser page with the compact identity header from the sign-in flow. The client opens D24 from outside RAFIQ. **Settings → Connections** (D23) provides setup instructions and manages existing grants. The driver returns to the requesting client through the applicable authorization flow. Report requests happen in the external client (X02), and the driver reviews and exports the finished report in RAFIQ (D17–D18). [D23–D24](../../SCREENS.md#d23-connections) · [X02](../../SCREENS.md#x02-external-mcp-agent)

1. **Review access for {client name}.** Identify the requesting client using authorization metadata returned by the provider. Show its metadata hostname, the validated return destination, and **Signed in as {driver account}** under the heading. Distinguish the client identity host from the callback host when they differ. If a supported desktop client returns to a local address, identify it as a local destination and show the actual host. Offer the full validated destination for inspection without exposing separately supplied OAuth request parameters. Keep the visual identity anchored by RAFIQ’s wordmark. Use the requester’s name and host as text even when no logo is available. A metadata-supplied name or logo carries no RAFIQ endorsement. [Clerk client metadata](https://clerk.com/docs/guides/configure/auth-strategies/oauth/client-id-metadata-documents) · [Clerk custom consent guidance](https://clerk.com/docs/react/guides/configure/auth-strategies/oauth/custom-consent-page)
2. **Choose permissions.** Show each supported permission in the current request as a labeled native checkbox with a plain-language summary and a separate disclosure trigger. Both checkboxes are empty when both scopes are requested. The single-scope variant shows only that requested permission. A checkbox changes the selection immediately. Opening its details changes only the disclosure. Use the visible triggers **Driving data details** and **Report authoring details**. Keep both disclosures independently expandable.
3. **Always private.** Keep the excluded categories visible in the normal reading flow, even with both disclosures closed. Add **You can revoke each permission in Settings → Connections.** The privacy summary appears above the decision actions.
4. **Decline** and **Allow selected** in one action row, with comparable size, contrast, and prominence. Start with a visible instruction, **Select a permission to allow access, or decline.** Keep Allow selected unavailable with zero choices and keep Decline available. Approval requires an explicit press of Allow selected. Give the approval button no initial focus and provide no select-all control or implied approval after sign-in, disclosure, navigation, or a timeout.

Use `colors.canvas`, `colors.ink`, `colors.accent-stone`, and Space Grotesk, the documented Mori substitute used in RAFIQ’s Settings briefs. Use flat dividers, `spacing.sm` (8 px) within label groups, `spacing.md` (16 px) for row padding, `spacing.xl` (24 px) between sections, and `rounded.md` where the established controls use it. Start with a 1440 px desktop reference and a proposed readable column of about 640 px, with 48 px outer desktop gutters and 20 px at the 390 px reference. Keep a single page scroll. Let names, hostnames, and action labels wrap at narrow desktop widths, 200% zoom, and 320 CSS px reflow. Stack the decision actions in reading order when they no longer fit side by side. [Design tokens](../../DESIGN.md) · [D19 Settings visual reference](D19-SHAPE.md) · [WCAG reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

The layout alternative paired the permission rows with a persistent **Always private** column on wide screens. It made the two data boundaries easy to compare at desktop widths, at the cost of more eye movement and a layout change at higher zoom. The approved single column keeps identity, permission descriptions, exclusions, and the decision in one reading path.

## Permission content

| Permission | Summary visible before choosing | Expanded explanation |
| --- | --- | --- |
| **Read driving data** (`driving:read`) | View approved summaries, analytics, and event details from your own driving sessions. | Session IDs and timestamps, duration and usable coverage, behavior and incident counts, and validated summary metrics with their units and methods. Event details include event ID, type, start time within the session, duration, and severity. |
| **Author reports** (`reports:author`) | Start a report job and submit a draft. You review and export the finished report in RAFIQ. | Start a session or personal-trend report, use its approved template and evidence, check its status, and submit a draft. This permission gives access to approved inputs for the client’s own authorized job. General access to driving data requires the separate Read driving data permission. |

**Always private.** The client cannot access raw camera media, incident clips or clip links, raw measurement series, contacts, precise location, finished report contents, or another account’s data. The client also cannot enable recording, run or control a monitoring session, change settings or live thresholds, create share links, or invoke Emergency Mode. Use plain text and a short list. D24 contains no driving-data preview, charts, clips, or report samples. ## States and return to the client

| State | Visible behavior and recovery |
| --- | --- |
| Checking request | Show **Checking authorization request…** in the main region. Wait for the client, destination, requested scopes, and driver eligibility before showing decision controls. |
| Signed out or lost sign-in | Show **Sign in to review this request** and use P04. Resume only a still-valid request after verification and any required onboarding. Present fresh unchecked choices. A switched account clears previous selections and revalidates the request and eligibility. A restricted account follows P07. |
| Valid request | Show the requester and exactly the requested supported permissions. Support read only, author only, both, and decline. Checking one never checks the other. A request for access the product cannot safely interpret or grant falls into the unavailable state. |
| Submitting | Keep context and selections visible. Show **Saving your decision…** and prevent duplicate or competing submissions while the outcome is pending. |
| Approval confirmed | Show **Permissions approved for {client name}** and list the permissions confirmed for this request. For a partial grant, identify which requested permission this decision did not grant. Use **Return to {client name}** when the qualified flow can show a RAFIQ receipt before return. Confirmed permissions appear separately in D23. |
| Decline confirmed | Show **Request declined** and **No permissions were granted for this request** when the return flow supports a RAFIQ receipt. A valid decline returns the provider’s denial to the client. Wording concerns this request, so it does not imply revocation of earlier grants. |
| Invalid, unsupported, or expired | Remove the decision controls. Show **This request is unavailable** or **This request expired**, as applicable, and **Start a new request from your client**. A return action requires a currently validated destination and a supported disposition. |
| Recoverable failure | Show **Couldn’t save your decision** and offer retry once the same driver, client, and request are confirmed current and the failed outcome is known. Preserve the current selections for that retry. For an unknown outcome, resolve status through a supported path before presenting success or retrying. |
| Return fails after a confirmed decision | Where the protocol supports this distinction, keep the confirmed outcome visible and offer a qualified return recovery. Do not ask for the same grant again solely to repeat a handoff. If the flow redirects directly, put the terminal outcome in the supported client handoff and show independently confirmed grant status in D23. |

## Accessibility and motion

- Use a meaningful page title, one main landmark, a skip link where header navigation warrants it, and a fieldset with a visible legend. Associate each scope summary with its checkbox. Tab moves through each checkbox and its neighboring disclosure before the decision actions. Space selects or clears a focused checkbox. A button-based disclosure supports Enter and Space and reports its expanded state. A disclosure control sits outside the checkbox label, with its own target and visible focus. Aim for 44 CSS px activation targets with sufficient spacing between adjacent controls. [Checkbox pattern](https://www.w3.org/WAI/ARIA/apg/patterns/checkbox/) · [Disclosure pattern](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/) · [WCAG target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- Show the checkmark and selected semantics immediately. Open or close details in place with a proposed 140 ms ease-out reveal and small chevron turn. Use no bounce, blur, or stagger. Keep focus on the disclosure control. Keep visually collapsing content out of the focus path. With reduced motion, show either endpoint immediately. The static fallback uses a native disclosure with instant changes.
- Render submitting, failure, and confirmed outcomes immediately. Use a single polite live region for progress or inline confirmation. If a new terminal view replaces the form, move focus to its heading and avoid announcing the same outcome twice. Keep errors adjacent to the action area and use text alongside icons. Treat a return transition as navigation. The authorization decision, status, and handoff have no animation dependency. [WCAG status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)

## Pen.dev handoff and release checks

Use editable components and state variants. Start from the RAFIQ foundations and sign-in identity treatment, with D19’s status, type and focus styling as a visual reference. The existing briefs record foundations `v3WGH`, D19 desktop `m9Bu2`, and D19 narrow `Tl48f`. The Pen editor did not return the canvas during shaping, so verify those references on open. Use synthetic content such as **Example Research Client** and `client.example.com`. Include a long wrapping name and hostname fixture and a missing-logo state. [Existing frame references](D20-SHAPE.md)

Show 1440 px desktop, 390 px narrow, and 320 CSS px reflow frames. Add variants for unchecked, read only, author only, both selected, each disclosure open, pending, approved subset, declined, sign-in, invalid, expired and retry. Annotate the disclosure’s collapsed and expanded endpoints, 140 ms timing, and instant reduced-motion endpoint. Pen represents the layout, motion endpoints, and outcome copy for the alternatives. Verify keyboard interaction, screen-reader announcements, reduced-motion behavior, identity and scope binding, and actual browser return in the frontend.

**Qualification dependency.** Clerk documents the requester identity, a custom consent route and a binary consent submission that forwards the original request parameters. Its public guidance does not establish the exact selected-scope grant or an intervening RAFIQ receipt. Qualify both with the client-neutral reference client before release. Prove that auth sign-in, zero selection, decline, expired or invalid requests, account switching, and duplicate submission cannot create an unintended grant. Prove each single-scope outcome and both together, the author-only boundary for general reads, independent revocation in D23, and that return and displayed scope match the provider-confirmed outcome. Qualify existing-grant behavior during reauthorization before finalizing its copy, including when a requesting client already has the other permission.
