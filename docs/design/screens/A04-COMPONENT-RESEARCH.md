# A04 Service Health — design proposal and component research

**Status** · Proposal for approval. **Mode** · Operate. This brief covers A04. Sample readings and timestamps are illustrative. The Pen.dev handoff follows layout and component approval.

## Job and entry

An Owner or Staff member with **View metrics** opens A04 after admin sign-in and MFA, from the permission-scoped admin navigation, or from an authorized link. A04 answers two questions in order. Is a service impaired now? What readings and timestamps support that conclusion? The screen shows operational aggregates. **Release Readiness** opens the nested A05 evidence view. Back restores the selected range, scroll position, and focus to the link. Other destinations follow the current admin grant. On sign-out, session expiry, or access revocation, clear affected data and follow the applicable admin access flow. Include only aggregate operational readings and approved evidence links. A04 actions read metrics or navigate to evidence.

## Signals and visual hierarchy

| Region | Visible information |
| --- | --- |
| Range and cutoff | **Last 1 hour**, **Last 24 hours** (default), **Last 7 days**, **Last 30 days**. A single-select control shows the applied range. Place the server **Query cutoff** beside it and show the display time zone. UTC is proposed as the shared admin display zone. Give every signal its own last update, unit, health state and denominator/sample count where relevant. Label current snapshots with their own **As of** time when different. |
| Key services | Frontend, API and worker where provided. Show service name, health text and icon, and latest evidence timestamp or specific reason. The cards report status at their observation time. They stay distinct from the historical totals in the trend panels. |
| Availability and performance | Three aligned plots with their own y-axes and a shared time window. **Uptime (%)** is successful scheduled checks ÷ observed scheduled checks, by service where data is supported. **API error rate (%)** is failed server requests ÷ eligible requests. **API p95 latency (ms)** is the 95th percentile of eligible API request durations for the represented window or bucket. Use the server’s p95 and sample size. Show counts alongside ratios and include a threshold line only when the approved threshold and scope are available. |
| Queues and storage | Session sync and report queue depth in jobs and oldest pending age as a duration. Show upload or worker observations where available. Show storage used and quota together in matching units, with percentage only when a valid quota is known. Use explicit as-of labels on point-in-time readings. A fresh depth of zero supports **No pending jobs** for oldest age when the readings refer to the same queue and observation. |
| Backup and deletion | Show last successful backup as a timestamp and backup lag as a duration. Give sample freshness its own label. Show aggregate deletion and purge progress with the available counts and overdue purge count where supported. Show **No sample** for an absent reading and add an approved reason if available. Avoid inferring completion from a 0 overdue count. |
| Emergency delivery | One row per channel, **Email** and **WhatsApp**, with independent qualification and runtime health, freshness and columns for **Pending**, **Accepted**, **Delivered**, **Failed**, **Unconfirmed**. Count distinct attempts created in the selected window by their recorded status at the query cutoff. Explain **Accepted** as provider acceptance and **Unconfirmed** as the recorded attempt status. A missing aggregate leaves its count cells unreported. An unqualified channel displays **Awaiting qualification** with a link to the A05 evidence and leaves its counts unreported. |

Use breaks in linear plots at missing or unavailable buckets, a labeled no-data state when there are no valid buckets, and a zero-baseline mark for confirmed zero on count or rate plots. Avoid temporal interpolation across missing bucket intervals. Show bucket start/end, metric, exact value and unit, counts, and data availability in the same readout for pointer and keyboard. One focus entry per plot with arrow-key inspection, optional click/tap or Enter to pin, Escape to clear, and a **View data** disclosure with an equivalent table. The chart, readout and table use the same bucket states. Sparklines are optional and supplemental. Give them a named metric, range and unit in adjacent text, use the same gap rules, and link to the full trend where one exists. Keep the displayed headline reading steady while inspecting historical points.

## Evidence and recovery states

| Evidence | Card / table | Plot or action |
| --- | --- | --- |
| Fresh evidence within approved threshold | **Healthy** with exact reading and timestamp. | Plot the valid bucket at its measured value. |
| Fresh evidence confirms degradation | **Degraded** with measured reading and reason or approved threshold where available. | Show the valid observation and keep the useful range context. |
| Fresh, confirmed service outage | **Unavailable · Outage confirmed** with a stop icon and observation time. | Plot any measured bucket value. A confirmed availability failure with observations can yield **0% uptime**. Missing points still appear as gaps. |
| Earlier sample has exceeded the approved freshness limit | **Unknown · Stale telemetry** with **Last sample** time. If a previous reading is shown, label it **Last known** apart from the current reading. | Keep valid historical points. Leave the interval after the last valid bucket unfilled. |
| Evidence is missing or insufficient | **Unknown · No sample** or **Unknown · Insufficient data**, as appropriate. Show an em dash with the reason and no invented timestamp. | Use a gap or **No samples in this range**. Zero checks or eligible requests leaves the corresponding ratio undefined and zero requests leaves p95 undefined. |
| Fresh, observed zero | Explicit **0** with unit and scope, such as **0 jobs**, **0 attempts**, or **0% (0 of 480 requests)**. The approved health state is evaluated independently. | Plot zero when defined. A channel can show zero in all five columns only if coverage confirms zero attempts in the window. |
| First load and range change | First load uses static skeletons with labeled regions. On range selection announce loading and keep controls and section positions stable. If previous data stays visible during a request, identify its applied range and cutoff until the new response commits. | Accept only results belonging to the latest requested range. Keep focus on the range control and commit the applied range, cutoff and results together. |
| Partial source error or empty response | Keep successfully loaded sections readable. Show **Couldn’t load [section]** with a section retry where the source supports it. Empty data returned successfully shows **No sample**. Prior authorized observations, when kept, retain their original range, cutoff and last-sample labels. | A recovery request stays on the selected range. If a retry returns a new snapshot, display its actual cutoff and avoid presenting retained values as part of it. |
| Entire read fails or permission changes | An initial request failure shows a page-level read error and **Retry**. Revocation, sign-out, and session expiry clear affected content immediately, including retained snapshots. | Distinguish **Couldn’t load Service Health** from a measured service outage and follow the authorized recovery path. |

Uptime zero describes observed failures. A count of zero describes an observed absence of activity. Both depend on explicit evidence. Keep qualification, telemetry freshness, request success and service health independently readable. A qualified channel can still have **Unknown** runtime health, including when an aggregate reports zero attempts.

## Keyboard, reflow and motion

- Use an admin navigation landmark, skip link, page heading and semantic named sections. Range options use single-select radio semantics with conventional arrow keys. The selector keeps focus through updates, and focus remains visible separately from selection. Section retry stays reachable, and completion feedback is announced once. Status badges are readable text and icons. Announce meaningful health transitions once per changed signal or as a grouped message, with no per-sample or timer announcements.
- Use native table structure, captions and scoped column/row headers. Keep row order stable during reads, refresh and retry. At a narrow desktop width or 200% browser zoom, wrap the toolbar, let cards flow to two columns or one as space allows, and stack the plots. At the equivalent of 320 CSS px, keep the page in a single reading column. A genuinely wide table can scroll inside a labeled keyboard-accessible region or become two labeled channel summaries exposing all five counts. Verify focus visibility and exact values at both scales.
- **Recommended motion:** immediate values, badge labels and chart geometry. Optionally glide the selected range accent for about **150 ms**, and reveal user-opened secondary detail for **150–180 ms** if selected. Keep status cues and evidence present throughout. Reduced motion and the all-static option use immediate updates, with the same focus, labels, loading, and recovery. Use a static skeleton. Odometers, pulsing outage indicators, line drawing on load, chart path morphing, and background row reordering all obscure the evidence during a scan.
- Pen can represent default and mixed states, chart breaks versus zero, selected/focused range, focused bucket/readout, scoped retry and narrowed layouts as static frames. An optional transition can be shown as endpoint frames with timing annotations. Live fetches, chart coordinates, keyboard handling, freshness evaluation and reduced-motion policy belong to the browser implementation.

## Contract items to resolve before implementation

- **Freshness and range evidence.** TRD requires approved per-signal thresholds and stale deadlines. The proposed response has health, timestamps and a shared metric reason, but no explicit stale reason, freshness deadline or bucket cadence. Confirm how the frontend can distinguish stale from missing, and how windows, bucket boundaries, partial buckets and no-sample intervals are conveyed. Confirm refresh cadence, if any. Pen states may show illustrative cases without fixed production values.
- **Emergency delivery source.** `HealthDelivery` supplies qualification and counts or null. It has no per-channel health, freshness timestamp or coverage indicator, and a null aggregate cannot express stale versus missing. Confirm the supporting fields or source before showing runtime claims or asserting fresh zeros. Keep **Awaiting qualification** independent of runtime state.
- **Queue and purge detail.** The signal enum lists general `queueDepth`, `oldestPendingJob` and `reportQueueDepth`, with no explicit queue dimension or separately named report oldest-pending age. It lists `purgeOverdue` without deletion/purge progress fields. Confirm mappings and available aggregates before filling those rows. Confirm which `Metric` fields, if any, carry exact numerator counts so rounded rates never produce fabricated counts.
- **Partial read and retry.** The draft API exposes a single range-based GET with a server cutoff. It does not define section retry, a pinned-cutoff read, or per-section read-failure metadata. A section-local retry trigger may re-read that range and re-render the complete returned snapshot. Confirm how successful sections and their original timestamps are preserved if the response remains partial.

## Approval

Choose **A · Status first** or **B · Trends first**. Choose **all-static**, **range accent only**, or specify the candidate IDs and motion you want. The suggested starting point is A with C01, C05 and C08, plus a first-party range cue only if approved. The UTC display zone and optional sparklines are independent choices. Sample-based freshness, release gates and telemetry schema gaps remain open implementation inputs.
