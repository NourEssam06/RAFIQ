# A03 Admin MFA Recovery

**Mode** · Operate. **Direction approved 25 November 2026.** Use **A**, the recovery code form with Owner guidance below, and **A03-C01**, static inline status and persistent confirmation. Use existing RAFIQ controls and standard form semantics.

An invited Staff member or Owner who has verified their sign-in but cannot use their authenticator opens A03 from the A02 challenge. They can redeem one saved, unused recovery code or ask another eligible Owner to reset their enrollment. In either case, recovery opens fresh authenticator enrollment in **A02**. Admin views and interrupted privileged actions remain gated until current verification and authorization succeed. ## Recovery paths

- **Use a saved code.** One persistent label, one masked text field that accepts a full paste, and explicit submit. Helper copy: “Use one of the recovery codes you saved during authenticator setup. Each code works once.” Keep the default keyboard capable of letters and symbols. The API permits 1–80 characters and defines no public pattern. Use empty/length validation on submit, avoid silent truncation or unconfirmed normalization, and let the server verify the code. Clear a stale inline error when the user starts editing a replacement. Keep the secret only in the current form while needed and clear it on definitive rejection, success, identity loss or exit. Exclude it from URLs, storage, analytics, replay capture and logs. [API recovery operation and RecoveryRedeem schema](../../API.md) · [WCAG accessible authentication](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html) · [W3C form notifications](https://www.w3.org/WAI/tutorials/forms/notifications/) · [NIST saved recovery codes](https://pages.nist.gov/800-63-4/sp800-63b.html#saved-recovery-codes)
- **Get help from an Owner.** Proposed visible copy: “Ask another RAFIQ Owner to reset your authenticator enrollment. After the reset, sign in again to set up your authenticator. Keep your recovery codes private.” The eligible Owner acts on the other administrator in A08 Staff Access, confirms the target, and completes fresh verification. A03 can recognize enrollment required on the affected administrator’s next verified entry. Show reset-specific confirmation only where the server provides reliable reset evidence. The approved flow defines no in-app request, delivery receipt, contact destination or waiting tracker. The last Owner’s loss of both factors goes through the audited deployment procedure outside A03. ## States and feedback

| State | Visible feedback and next action |
| --- | --- |
| Ready | One labeled field, the single-use helper, **Verify recovery code** and Owner guidance. **Back to authenticator** returns to A02 only while that challenge is still allowed. |
| Empty or overlong | “Enter a recovery code.” or “Enter a recovery code of 80 characters or fewer.” Place the error beneath the field, associate it programmatically, and focus the field. |
| Submitting | Show **Verifying recovery code…** immediately in a stable action/status area. Keep one request in flight and announce pending once. Use the same button footprint throughout the request. |
| Invalid | “We couldn’t verify that recovery code. Try another unused code.” Associate the message with the field and return focus there. |
| Used | “This recovery code has already been used. Try another unused code.” Use only for an explicit, safe server outcome for the verified identity. Fall back to the invalid-code wording for ambiguous responses. |
| Rate-limited | “Too many attempts. Try again in [time].” Use the server’s `Retry-After` when supplied. Otherwise use “Too many attempts. Try again later.” Keep the Owner guidance usable. Announce the restriction once and announce availability once when known. |
| Connection lost or result unknown | “We couldn’t confirm what happened. Check your recovery status.” Re-read authorized entry state before allowing another explicit attempt. A code can be consumed even if its response is lost. If entry reports enrollment required, use the neutral enrollment handoff unless the specific success was confirmed. |
| Identity expired or access revoked | Clear the form. Offer **Sign in again** through A01 for an expired identity. For revoked access, show the current access restriction and an applicable sign-out action. An in-flight result for an old identity cannot replace either state. |
| Code verified | On confirmed redemption, replace the field and action with **Recovery code verified** and “Set up your authenticator again to regain admin access.” Primary action **Set up authenticator** opens fresh A02 enrollment. Keep the confirmation available until the user continues. |
| Owner reset confirmed | With authoritative reset evidence use **Authenticator reset** and **Set up authenticator**. With only an enrollment-required state, use **Set up your authenticator** without naming a cause. A02 verifies enrollment and issues fresh recovery codes. |

**Contract details to resolve before building.** The recovery operation says it opens secure re-enrollment, but the success example shows `AdminEntry.state: active`. `AdminEntry` also defines `enrollmentRequired`. Confirm the recovery response and the authoritative entry state after both recovery paths. A03 must treat recovery as enrollment-only and keep old admin session authority invalidated. SCREENS calls for distinct invalid and used variants, while the recovery operation references generic errors. Confirm privacy-safe problem codes before mapping those variants. Confirm a team contact channel before adding any Owner contact link. ## Components and motion research

- **Reuse from RAFIQ.** Auth shell and wordmark, primary action and back-link styling, and the inline identity status pattern. `Yh4JZ` (Horizontal status row) is an existing reference for status alignment. The `P8LWJ8` compact arc uses a Pen shader. Its visual form is reusable, while a browser version can use a small CSS arc if needed.
- **Standard components.** Native form, one masked text field, inline error, a polite status region, secondary navigation link and a persistent heading with a button for the next step. Default to stable field dimensions, immediate focus and error treatment, and one visible status message. Avoid a segmented OTP field because the recovery code is a variable-length string. A labeled pending state conveys progress without a stepper or percentage. ## Pen.dev handoff and acceptance

Draw the ready desktop frame, representative narrow and zoomed frames, and a state strip for inline errors, submitting, and rate limited. Include the visible Owner guidance, access-loss and unknown-result states, the verified-code and confirmed-reset enrollment handoffs, and the neutral enrollment-required variant. Use synthetic field values or masking dots. Annotate the trigger for each instant state change. Pen.dev can represent the visual hierarchy and state sequence. The frontend owns credential handling, announcements, keyboard focus, cooldown and authorization.

- Confirm the one field accepts keyboard entry and full paste, remains labeled at zoom, and exposes an associated error through `aria-describedby` and `aria-invalid` where applicable. Tab order follows reading order and all controls keep visible focus.
- Verify one pending request, a readable pending label with motion disabled, and one announcement per meaningful transition. After a field error, focus the field. After the confirmed replacement, focus its heading, then the next Tab reaches **Set up authenticator**. Check A02 route entry and back navigation by keyboard.
- Verify both authorized recovery paths reach fresh A02 enrollment, the affected prior sessions lose admin authority, and code reuse is rejected. Verify revocation and an unknown network result never admit the user to a protected view or restart the prior privileged action. Audit recovery without secrets.
