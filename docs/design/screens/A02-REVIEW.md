# A02 Authenticator enrollment and challenge

**Proposal for approval · Operate · Admin web**

A first-time or recovering Owner or Staff member pairs an authenticator, proves it works, and saves their recovery codes. A returning admin verifies the current sign-in. An admin already at a privileged form verifies again for the named action. A01 establishes the verified identity and eligible admin entry. A03 owns recovery and returns an eligible admin to fresh enrollment. A07 and A08 retain ownership of privileged forms and their outcomes. For step-up, replace the body of the originating confirmation dialog with a verification phase. Keep the action, authorized target, consequence and relevant approved reason visible. Keep one dialog, with a clear final commit action owned by the originating form.

Reuse P03/P05’s six-slot outline and cyan verification button, the compact RAFIQ wordmark and header pattern, and the existing confirmation dialog’s hierarchy, controls and focus treatment. Use the documented warm canvas, ink and stone roles, existing Space Grotesk substitute for Mori and the 8/16/24 px spacing roles. Start at 1440 px with a roughly 480–520 px reading column for A and a split panel for B only while both columns fit. Check 1024 px, 390 px, 200% browser zoom and 320 CSS px reflow. Let setup guidance, keys, long targets, status and actions wrap. Keep QR square, the OTP affordance within the column, and all focused controls visible when the dialog or page scrolls. The mobile keyboard should leave an ordinary scroll path to Verify. ## Enrollment and verification behavior

| State | What the admin sees and does |
| --- | --- |
| Preparing setup | **Preparing authenticator setup…** in the panel, with the setup actions available once an eligible response arrives. Show a clear retry path after a confirmed temporary failure. |
| Connect authenticator | Explain how to add a RAFIQ account in an authenticator app. Render the QR locally from the private setup URI. **Enter a setup key instead** discloses a selectable key and the same-device instructions. Show **Copy setup key** alongside it if clipboard controls are approved. The text path and the QR lead to the same enrollment. |
| Ready to verify | **Authenticator code** and **Enter the 6-digit code from your authenticator app.** Use one labeled text input with numeric input mode, `autocomplete="one-time-code"` where supported, and six visual slots drawn from the same value. Preserve leading zeros, allow full-code paste, selection, replacement and autofill, and tolerate ordinary whitespace grouping before validation. Submit explicitly with Verify or Enter, including after paste/autofill. Six digits is the input format. |
| Verifying | Keep the form and button in place. Announce **Verifying code…** once and block duplicate submission while pending. Keep a usable way to cancel step-up. Only a successful current response can advance the active flow. |
| Incomplete, rejected or reused | Associate **Enter all 6 digits** with the field for incomplete input. For a rejected or reused TOTP, use **This code didn’t work. Enter a new code from your authenticator app.** Clear the rejected value, return focus when correction is needed and allow fresh input. The shared wording is usable when the API exposes a safe generic response. |
| Expired setup | Remove the expired QR, key and entered code. Show **Setup expired** and **Start setup again** if the server still allows enrollment. Keep verified identity and eligibility checks on the new attempt. |
| Rate-limited | Show **Too many attempts. Try a new code later.** If the server supplies `Retry-After`, give a readable retry time. Announce the lockout and eligibility to retry once each, preserve a route to the applicable recovery or exit, and recheck current authority before enabling a fresh explicit attempt. |
| Offline, unavailable or unknown outcome | Keep a readable status and safe exit. On reconnection, resolve admin entry and current authority before another attempt. A dropped enrollment verification response may have committed setup and issued the one-time codes. Show the codes as unavailable if setup committed and the response was lost. Use the authorized recovery or reset route when needed. Keep the privileged confirmation pending until fresh verification is established. |
| Verified | Enrollment shows **Save recovery codes** immediately on authorized receipt. Returning sign-in goes to an authorized requested destination, Service Health when permitted, or the first permitted view. With zero permitted views, explain the access status and offer sign-out. For step-up, show **Identity verified** on the returned confirmation and restore focus to the appropriate control. Verification and the action result have separate status copy. |
| Authorization changed | On revocation, session loss, identity switch or loss of the action’s permission, close the affected flow, clear credentials and protected context the admin can no longer access, discard late success responses and show the current access state. Offer fresh sign-in or an eligible return where applicable. If authority and target eligibility remain valid, step-up cancellation or a recoverable failure can restore the original draft and approved reason. |

The enrollment challenge uses the active enrollment ID and `expiresAt`. Sign-in challenge and step-up use the same endpoint and require a current, unused TOTP. Keep fresh proof tied to the verified Clerk session server-side, and recheck both freshness and current permission or eligibility when the originating action commits. Recovery via A03 requires verified identity and consumes one code. It invalidates affected admin verification and grants before re-enrollment. Entering A03 from a privileged flow abandons the privileged continuation. Full page and dialog states use the same form semantics. ## Recovery codes and copy feedback

- **One-time display.** Lead with **Save recovery codes** and “You’ll only see these codes once. Store them somewhere secure. Each code works once if you lose access to your authenticator.” Show the actual issued array as selectable text in an accessible list, one code per row at narrow widths. Preserve characters, case and reading order when wrapping. The API specifies at least one code and up to 80 characters per code, with count and display format still open. Announce the new heading without reading every code automatically. Use visibly fake placeholders and a non-scannable QR drawing in Pen.dev. [RAFIQ API](../../API.md) · [Login.gov backup-code pattern](https://www.login.gov/help/create-account/authentication-methods/backup-codes/)
- **Copy options.** Recommend explicit **Copy recovery codes** (one code per line), with manual selection available even when the browser denies clipboard access. Use the same feedback pattern for **Copy setup key** when approved. Keep keyboard focus on the button, report success only after clipboard write resolves and show a selectable fallback after failure. A stable accessible button name and adjacent status such as **Recovery codes copied** work with either visual treatment. Tell the admin to paste into a secure location. Clipboard history is outside RAFIQ’s control. Download and print controls would create additional credential copies and need a separate product decision. [Clipboard API](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/writeText) · [WCAG status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)
- **Exit options.** Recommend **I’ve saved my recovery codes** with **Continue** and a visible explanation if confirmation is missing. Copying leaves that acknowledgement under the admin’s control. The lighter alternative is **Continue** with the same one-time guidance and no required checkbox. Either treatment is a presentation choice. Enrollment is already verified when this screen appears. Continuing, leaving, reloading or losing authority clears the displayed codes. Browser Back and restores must not resurrect them. Resolve current authority and the next eligible screen after reload. Keep QR data, setup keys, OTP values and recovery codes out of URLs, caches, persistent browser state, diagnostics, audit and analytics. Use private, no-store responses and transient client state. The server stores encrypted TOTP secrets and hashed single-use recovery codes. [RAFIQ private response and security requirements](../../API.md#12-security-and-reliability-requirements) · [MFA storage and recovery](../../TRD.md#6-external-protocols)

## Handoff checks and open contracts

- Storyboard both the pre-dashboard route and the in-place step-up dialog. Include setup QR and manual key, OTP focus and paste, rejected/reused, pending, throttled, expired, saved codes, copy denied, session or permission lost, and verified return without an automatic privileged commit. Exercise foreground and restored tabs, slow responses and authorization changes mid-request. Verify the A03 transition re-enters fresh setup after recovery. [Screen requirements](../../SCREENS.md#a02-authenticator-enrollment-and-challenge)
- Check keyboard-only and screen-reader paths, focus on meaningful phase changes, visible focus, one tab stop for the OTP field, label and error association, Enter submit, Escape/cancel and focus return to the opener or nearest authorized control on exit. Use motion-free screenshots plus a separate storyboard for any approved motion. Test clipboard denied, a leading-zero code, spaced paste, long recovery codes, slow verification, reduced motion, narrow width and zoom. [Modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) · [WCAG reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- Confirm implementation contracts for recovery-code count and format, fresh MFA window, retry metadata, safe problem-code distinctions, and how mounted screens learn about permission changes without waiting for the next user action. §11 gives the generic HTTP handling. The entry response resolves authorization and next step. Step-up freshness after a lost response and recovery after lost one-time issuance still need explicit handling. Keep the corresponding waiting and uncertain-outcome states in the design. ## Approval

Choose **A** or **B** for enrollment, **Copy with saved confirmation** or **Copy with Continue** or **Manual selection with Continue** for recovery codes, and **static feedback** or **A02-C05 copy icon crossfade**. Individual component IDs can be selected or replaced. Recommended combination is **A + copy with saved confirmation + static feedback** using **A02-C01, A02-C03 and A02-C06**. The final Pen.dev handoff follows explicit approval.
